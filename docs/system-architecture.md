## 1. Core idea (the reframe)

Meal planning is **not** a one-shot optimization ("make the optimal week, this week"). The best system is a **learning relationship**: each week is one turn in a loop, and personalization that compounds is where it's won.

```
know the household → plan → watch what they actually do → learn → plan better
```

A generic planner that's "optimal" this week and identical next week loses to a mediocre one that *learns you* by week six. The architecture below exists to make that loop real.

---

## 2. The shape — two components, one membrane, a loop

```
              ┌──────────────── USER MODEL (per household) ────────────────┐
              │ structured features · narrative summary · confidence/recency │
              │ per-member profiles                                          │
              └──────▲────────────────────────────────────────┬────────────┘
                     │ writes (async)                          │ reads (sync)
        ┌────────────┴─────────────┐              ┌────────────▼─────────────┐
        │  PERSONALIZATION (async) │              │  PLANNING (sync / week)  │
        │  signals → stats →       │              │  code: feasible frontier │
        │  periodic LLM reflection │              │  LLM: pick the point     │
        └────────────▲─────────────┘              └────────────┬─────────────┘
                     │ signals                                  │ plan
                     └──── household cooks / skips / edits / rates ◀──┘
```

Two components on **different clocks**, **decoupled through the user model** — they never call each other. Planning reads the model; Personalization writes it. The user model is the membrane.

This is the key structural decision: connecting through a **persisted shared artifact** (not agent-to-agent calls) keeps personalization async (no latency on planning), keeps each side testable, and avoids a chatty multi-agent loop.

---

## 3. Component 1 — Planning Agent (sync, per week)

The per-week engine. Current strategy in `plan-selection-strategy-B-rank-assemble.md` (alternative in `-A-frontier.md`); in brief:

- **Code generates a small frontier of *feasible* week-plans** — each satisfies every hard constraint (allergy, dietary lock, budget cap, coverage) with all real numbers (cost, time) computed correctly. Generated by synergy-aware greedy now; a solver later if needed.
- **The LLM picks the plan** that best matches the household's current user model + any stated priorities for this week. It may reassign days and propose at most one swap.
- **Code validates and finalizes** — the LLM never does arithmetic and can never pick something infeasible.

**Change from the standalone design:** the planner now reads the **user model** as its primary preference input (not just a one-off `priority_profile`), and it **emits the proposed plan** as context for interpreting later signals.

---

## 4. Component 2 — User Model (the membrane)

A persisted, evolving model of the **household**. The highest-value, least-built piece — this is the moat. It has two forms because it has two consumers (code scoring and LLM judgment):

- **Structured features** (for code): cuisine affinities, ingredient likes/avoids, effort tolerance by day-of-week, repetition tolerance, budget behavior, nutrition lean.
- **Narrative summary** (for the LLM): a few sentences capturing the *feel* of this household.
- **Confidence + recency** per belief: weak/old signals decay so the model stays current and doesn't ossify.
- **Per-member sub-profiles**: household structure lives here. Multi-eater handling is *structure in the model*, not a separate top-level agent.

> Open: exact schema, how structured vs narrative are kept in sync, how confidence/decay are computed. See §9.

---

## 5. Component 3 — Personalization Agent (async, cross-week)

Mostly a **data store + stats + a periodic LLM reflection pass** — *not* a constantly-running agent:

- **Code** stores signals and computes features (frequencies, averages, trends).
- **An LLM reflection pass** runs after a week (or on enough new signal): it reads behavior → **latent taste** — the genuinely fuzzy "read between the lines" judgment a formula can't capture (e.g. *"they say variety but reliably cook the same 3 comfort meals on weeknights — they value comfort more than they admit"*) — and updates the user model.
- Runs **async**, never inside a planning request. It **shapes the model; it never decides a plan.**

---

## 6. The signal pipeline (what feeds the loop)

The household's behavior is the training signal. Captured by the app, stored by code, consumed by Personalization:

- **cooked / skipped** a planned meal
- **edited** the plan (the strongest signal — an edit is an explicit correction)
- **rated** a meal
- **time-to-cook**, day cooked vs. planned
- (later) photos, leftovers logged, waste logged

Treat **edits as first-class learning input**, not just UI friction.

---

## 7. The code/LLM boundary (the sharpened rule)

The boundary is **not** "formula vs. no formula." It is **computation vs. pattern-recognition**. Edge-case explosion is the tell: when code becomes a brittle pile of `if`s simulating a behavior, the thing was never computation — it's pattern matching, and pattern matching over messy inputs is what models are for.

**Discriminator — it's the *input*, not the difficulty:**
- **Clean, bounded inputs + hairy logic** → **code/solver.** Cases are enumerable and verifiable; an LLM adds unverifiable non-determinism. *Hard ≠ LLM.*
- **Messy, open-world inputs + endless cases** → **LLM-eligible.** Reality doesn't fit clean categories; a model generalizes instead of enumerating.

| Task | Nature | Owner |
|---|---|---|
| Cost / budget / coverage / time totals, feasibility | computation (clean) | **code/solver** |
| Frontier generation | computation (combinatorial) | **code** (greedy→solver) |
| Pick plan vs. priorities; "coherence as a week" | no formula (taste) | **LLM** |
| Ingredient matching — the messy long tail | pattern, open-world input | **LLM** (offline→data, fast-path, verify) |
| Recipe parse / fuzzy tagging | pattern, messy text | **LLM** (offline where possible) |
| Behavior → latent taste (reflection) | pattern / no formula | **LLM** (async) |
| Signal storage, stats | computation | **code** |

**Discipline that keeps the pattern-recognition cases honest (or this slides into LLM-everything):**
1. **LLM the residual, not the whole thing** — cheap deterministic rules handle the clean majority; the LLM only takes the cases that defeat the rules.
2. **Prefer LLM *offline → data*** — use the LLM to *build* alias/substitution/tag tables once; code matches deterministically at runtime; cache new resolutions.
3. **LLM proposes, code verifies** — the matched ingredient must exist; the parsed quantity must be a number. Wrap fuzzy output in a deterministic check.
4. **Let the residual shrink into code over time** — as resolutions cache, the LLM fires less; the problem migrates back toward code.

> Worked example: **ingredient matching.** Exact-id + alias handles the clean majority; the long tail of OCR'd / scraped / free-text ingredient strings is the edge-case swamp → embedding + LLM residual, cached as data, verified against the ingredient table.

## 8. Build order (by lever — where "best" is actually won)

Invest in this order (success metrics in `meal-planning-problem-statement.md` §2):

1. **Feasibility substrate + Planning Agent** — table stakes. Mostly designed. Ship it.
2. **User Model + minimal Personalization loop** — *the moat.* Start tiny: store signals, one weekly reflection pass, a simple model the planner reads. Makes week 10 ≫ week 1.
3. **Fit-to-life + mid-week flexibility** — effort/schedule awareness; re-plan from "I skipped Tuesday." Drives execution.
4. **Trust & control** — plan reasons + frictionless edits (edits feed lever 2).
5. **Conditional** — household negotiation (as conflict grows), solver upgrade (multiple hard caps / diversity collapse), richer taste model (embeddings / learned). Only when data demands.

Heavier machinery (multi-agent, solvers) lives at lever 1 (solvers for hard feasibility math) or lever 5 (negotiation for conflicting households) — **not** levers 2–3, where the wins actually are.

---

## 9. What to validate (don't assume)

- **Frontier diversity** (planning) — do the candidate plans genuinely span the trade-off space, or collapse to near-identical menus? If collapse is common, the LLM's choice is cosmetic → move to a solver. *Validate empirically first.*
- **Does the loop move the metrics?** — instrument acceptance rate, edit rate, cook-through rate, week-over-week retention. The user model only earns its complexity if these improve over time.
- **Cold start** — how good can week 1 be before any learning? (Determines first-impression and churn.)
- **User-model schema & decay** — what it holds, how structured/narrative stay in sync, how confidence/recency are computed.
- **Reflection quality** — does the LLM reflection produce *useful* model updates, or noise? Needs eyeballing on real signal.

---

## 10. Principles (recap — the rules of the game)

1. Computation → code (solver if hard). Pattern-recognition over messy inputs → LLM (residual, offline→data, verify, shrink over time).
2. **Hard ≠ fuzzy.** Complicated-but-definable math is a job for a better algorithm, not the LLM.
3. **Code measures, the LLM weighs.** The LLM never does arithmetic and never produces the number the user sees.
4. **Hard constraints are inviolable** — enforced by code; the LLM optimizes preferences only within the feasible region.
5. **Fewest LLM calls that do the job.** No LLM orchestrating the pipeline, no LLM sequencing tools, no LLM doing math. More LLM/agents only for a real second stakeholder or a learning-over-time loop.
6. **Edits are both a safety backstop and a signal.**
7. **Design for the loop, not the one-shot.**

---

## 11. Decision log (why it's this shape)

- **Two components, not one** — planning (sync, per-week) and personalization (async, cross-week) are genuinely different jobs on different clocks. Principled separation, not artificial decomposition.
- **Connected by a shared user model, not agent-to-agent calls** — keeps personalization async/decoupled, testable, latency-free for planning.
- **Personalization is store + periodic reflection, not a live agent** — only the behavior→taste read is genuinely LLM-shaped.
- **Household is structure inside the user model** — per-member sub-profiles, with explicit negotiation only as a conditional planning behavior (lever 5), not a third top-level agent.
- **Boundary is computation vs pattern-recognition** — sharper than "formula vs none"; correctly routes ingredient matching / parsing / reflection to the LLM without leaking cost/feasibility there.
- **Multi-agent is a means at levers 1 & 5, never the aim** — the wins are the learning loop and fit/flexibility, neither of which is multi-agent.

---

*The stable spine is: a feasibility-correct per-week engine + a personalization loop connected by a household user model, with the LLM used only for taste, messy-input pattern-recognition, and behavioral reflection. The formulas, the user-model schema, and the reflection internals are meant to evolve — re-open them as real data comes in.*
